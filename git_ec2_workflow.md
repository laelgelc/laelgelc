# Git Workflow Guide: Multi-EC2 Processing

This guide ensures you can develop continuously on your local machine while multiple EC2 instances process massive datasets in the background without any Git conflicts.

## Phase 1: Immediate Actions (While EC2 #1 is running on `main`)

Since your first EC2 instance is currently running on the `main` branch and expects to push there, you must "freeze" your local `main` branch to avoid blocking it.

1. **Move your current work to a new branch:**
   On your local machine, immediately create and switch to a new branch for your next source.
```shell script
git checkout -b feature/the_jerusalem_post
```

2. **Develop and commit safely:**
   You can now create the new directory (`cl_st1_ph1_melina/the_jerusalem_post`), write your scripts, and commit your changes. 
3. **Push the new branch:**
   Push your work to the remote repository. Because it's on a separate branch, it is completely invisible to EC2 #1.
```shell script
git push -u origin feature/the_jerusalem_post
```


## Phase 2: When EC2 #1 Finishes

Once the first EC2 instance completes its job, commits the data, and successfully pushes to the remote `main` branch:

1. **Update your local `main`:**
```shell script
git checkout main
   git pull origin main
```

   *(Your local `main` now has all the data and logs generated by EC2 #1).*
2. **Return to your development branch:**
```shell script
git checkout feature/the_jerusalem_post
```

   *(Optional)* If you want to bring the new data from `main` into your current branch:
```shell script
git merge main
```

## Phase 3: The New Standard Workflow (For EC2 #2 and beyond)

From now on, no EC2 instance should run directly on `main`. You will use the **Branch-per-Source** method. Follow these steps for `the_jerusalem_post` (and eventually `al_jazeera`, etc.).

### Step 1: Local Development
Whenever you start a new source, branch off `main`:
```shell script
git checkout main
git pull origin main
git checkout -b feature/new_source_name
```

Write your code, commit, and push the branch to the remote repository:
```shell script
git add .
git commit -m "Add code for new_source_name"
git push -u origin feature/new_source_name
```


### Step 2: EC2 Execution
When you log into your new EC2 instance to process this source, tell it to use the dedicated branch:
```shell script
# Clone the repository
git clone <your-repo-url>
cd <your-repo>

# Switch to the specific feature branch
git checkout feature/new_source_name

# Run your processing script (e.g., using run_python_ec2.sh)
nohup bash run_python_ec2.sh ...
```


When the script finishes, the EC2 instance should commit the generated files and push them back to **its specific branch**:
```shell script
git add data/ logs/
git commit -m "Add processed data for new_source_name"
# Push to the branch it is currently on
git push origin HEAD
```


### Step 3: Merge and Clean Up
Once the EC2 instance has pushed the processed data, merge it into your main project on your local machine:
```shell script
git checkout main
git pull origin main

# Merge the completed job
git merge origin/feature/new_source_name

# Push the merged data to main
git push origin main
```

You can now safely delete the feature branch, as the data and code are safely in `main`:
```shell script
git branch -d feature/new_source_name
git push origin --delete feature/new_source_name
```


### Summary of the New Standard:
* **Local Machine:** Creates branches, writes code, merges completed data.
* **EC2 Instances:** Check out specific branches, run jobs, push data back to those branches.
* **Result:** You can run as many EC2 instances simultaneously as you want, and you can keep coding locally all day without ever seeing a Git conflict.
